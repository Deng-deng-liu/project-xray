# 证据政策

## 一句话原则

代码只能证明“这里有什么”，不能自动证明“为什么这样做”或“当时发生了什么”。

## 四种陈述

| 类型 | 可以写什么 | 不能写什么 |
|---|---|---|
| `FACT` | 代码、配置、DDL、构建文件中直接可见的事实 | 推测的设计动机、线上结果 |
| `INFER` | 基于证据的风险路径，使用“可能”“需确认” | 把推断写成已发生事实 |
| `CLAIM` | 用户提供的简历或项目描述 | 未经代码验证就说“造假” |
| `ADVICE` | 改进方向、验证步骤、面试表达 | 编造收益、指标或实施结果 |

## 证据包

单个证据使用 `[E###] path:start-end`。架构题、选型题和场景题应尽量使用多个证据：

```text
[E002] pom.xml:21
[E007] src/main/java/.../RedisConfig.java:18
[E011] src/main/java/.../OrderService.java:57-66
```

证据行号是触发问题的锚点，不是设计动机的证明。代码中出现 Redis，只能证明“项目使用了 Redis”，不能证明“当时因为 QPS 高所以选了 Redis”。

## 置信度

- `verified`：直接代码事实。可以说“代码显示……”。
- `likely`：模式明确，但缺少 DDL、调用链、配置或业务上下文。必须写“需要核实”。
- `uncertain`：只能作为追问线索，不能进入高危坑统计。

## 严重度

- `high`：可能造成数据错误、安全问题、明显故障或严重性能退化。
- `medium`：维护性、稳定性或性能风险，需要结合场景确认。
- `low`：可讲点、待办项或需要复核的设计选择。

只有 `high + verified` 才能写“高危坑”。`high + likely` 写成“高危候选，需核实”。

## 禁止编造

禁止自行补充以下内容，除非扫描结果、用户输入或仓库文件明确提供：

- 线上故障、事故次数、故障时间
- QPS、TPS、并发量、用户量、数据量
- 响应时间、耗时、吞吐量
- 团队人数、开发周期、上线时间
- 业务规则、客户名称、商业指标
- “当时是因为……才这样设计”
- “已经被面试官问过”“很多人都会踩”

## 推荐措辞

- 事实：`代码显示……`
- 推断：`这可能意味着……`
- 不确定：`仅凭当前证据无法确认……`
- 需要本人确认：`可能的形成路径是……请确认是否属实。`
- 改进：`如果要在面试中讲清楚，建议先确认……`
- 简历声明：`简历提到 X；代码中未找到直接证据，暂标记为待核实。`

## 简历声明核验

如果用户提供简历描述，逐条标记：

- `代码可验证`：有直接证据，引用 `E###`
- `部分可验证`：有技术使用，但规模、效果或职责无法验证
- `未找到证据`：仓库中未发现对应实现，不等于造假
- `需要本人确认`：涉及业务背景、上线效果、个人贡献

不要把“没搜到”写成“没有做”。搜索范围、私有代码和未提交分支都可能造成遗漏。

## 密钥与隐私

- 报告只显示字段名，值统一写成 `***REDACTED***`。
- 不复制完整连接串、Token、密码、私钥。
- 不执行仓库代码，不读取环境变量中的真实值。
- 不把扫描结果上传到外部服务；除非用户明确要求。

## 校验器会检查什么

- 所有 `[E###]` 是否存在于 `signals.json`
- 带 `Q` / `F` 编号的段落是否至少有一个证据
- 固定总结句是否存在
- “高危坑”数量是否等于 `high + verified` 数量
- 是否出现无来源的 QPS、耗时、用户量等指标
- 是否残留未脱敏的敏感值或 `[TODO]` 占位符

校验通过不等于事实一定正确，但可以挡住最常见的编造和漏证据问题。


## 代码证据图

- 项目题和风险卡应嵌入 `assets/E###.png`。
- 图片由 `scripts/render_evidence.py` 从扫描器已脱敏的 `snippet` 生成，不允许绕过脱敏重新读取原始敏感内容。
- 自动生成的图是 IDE 风格代码卡，不等于真实 IDE 截图；报告中不要声称“这是 IDEA 实时截图”。
- 用户提供的真实 IDEA 截图可以放在 `assets/` 并按 `E###.png` 命名覆盖默认图。
- 一张图只展示一个证据；多证据题按证据编号顺序展示多张图。
- 图片应紧跟在题目标题下方，再写证据行和答案；不要让读者先读一大段答案才看到代码。
- 图片必须保留文件名、行号和关键行高亮，方便面试时回到代码。
- 如果图片生成失败，应在报告中明确标注图片缺失，不能编造截图内容。


## 改前 / 改后图

- `E###.png` 表示当前代码证据。
- `E###-after.png` 表示建议修改，不是项目原有代码。
- 只有 `fixes.json` 中明确提供 `after_snippet` 时才生成改后图。
- 报告必须把改后图标注为“建议修改”，不能混写成现有实现。
- 修改建议要尽量最小化，不要顺手重写整个类。
